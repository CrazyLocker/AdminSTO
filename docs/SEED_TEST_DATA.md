# Наполнение базы тестовыми данными

Инструмент `tools/seed_test_data.py` наполняет рабочую базу AdminSTO
(`autoservice.db`) демонстрационным набором клиентов, заказов и статусов
лояльности. Нужен для приёмки, ручного тестирования и демонстраций
заказчику: на пустой базе не видно ни уровней лояльности, ни скидок, ни
категорий услуг.

## Требования

- Python 3.8+ (только стандартная библиотека, ставить ничего не нужно);
- приложение AdminSTO должно быть **закрыто** — SQLite не даст писать в
  файл, который держит запущенный процесс;
- на Windows путь к базе указывается через прямой слэш:
  `--db T:/AdminSTO/autoservice.db`.

## Быстрый старт

```bash
# 1. Только сгенерировать SQL (база не меняется)
python tools/seed_test_data.py --db T:/AdminSTO/autoservice.db

# 2. Выполнить в базе (перед записью автоматически делается копия)
python tools/seed_test_data.py --db T:/AdminSTO/autoservice.db --apply

# 3. Перезалить поверх уже налитых данных
python tools/seed_test_data.py --db T:/AdminSTO/autoservice.db --apply --force
```

Флаги:

| Флаг | Что делает |
|---|---|
| `--db <путь>` | обязательный, путь к `autoservice.db` |
| `--apply` | выполнить SQL в базе; без флага скрипт только печатает отчёт |
| `--force` | сначала удалить ранее созданные тестовые строки (клиенты 2–12, заказы по ним, справочники 1–9/1–7), затем вставить заново |
| `--sql-out <путь>` | куда сохранить SQL (по умолчанию `tools/seed_test_data.sql`) |
| `--backup` | делать копию базы; с `--apply` копия создаётся и так |

Резервные копии складываются в `.tmp/seeds/backup-<дата>-<время>/autoservice.db`
внутри репозитория, а не в папке заказчика.

## Как данные согласованы с логикой приложения

Скрипт повторяет правила `LoyaltyService`, иначе база показывала бы статусы,
которые приложение никогда бы не выдало:

- **Звезда ТО** — закрытый заказ с услугой категории `MAINTENANCE`, при
  разнице пробега с предыдущим ТО в интервале 5 000–10 000 км (первое ТО
  всегда даёт звезду), максимум 5. Поэтому у клиентов 4–7 заказы ТО идут с
  пробегом 8 000 → 15 000 → 22 000 → 29 000 → 36 000 км (шаг 7 000 км).
- **Сумма тюнинга** — стоимость услуг категории `TUNING` плюс цена запчастей
  `TUNING` из заказа: Stage 1 — от 30 000 ₽, Stage 2 — свыше 100 000 ₽,
  Stage 3 — свыше 300 000 ₽.
- **Категория услуги** резолвится по `service_id`, затем по имени — поэтому
  имена услуг и запчастей в заказах совпадают с каталогом.
- **`orders.total`** равен сумме `order_services.price` и
  `order_parts.price * quantity` — ровно то, что вычисляет
  `WorkOrder.recalculateTotal()` при загрузке.
- **`last_repair_date`** заполняется датой последнего закрытого заказа.
- Даты хранятся в формате `dd/MM/yyyy`, идентификаторы заказов — в формате
  приложения `ZAK-ДД/ММ/ГГ-NNNN`.

Перед генерацией SQL скрипт вызывает `verify_consistency()`: она
пересчитывает звёзды и тюнинг по заказам и падает, если ручные значения в
справочнике клиентов с ними не совпадают. Это защищает от «красивого», но
неверного набора данных.

## Самопроверка после заливки

После `--apply` печатается отчёт:

- количество строк по таблицам;
- клиенты со звёздами, суммой тюнинга и вычисленным Stage;
- все заказы со статусом, суммой, пробегом, услугами и числом запчастей;
- сводка: сколько закрытых и открытых заказов, результат
  `PRAGMA foreign_key_check` и `PRAGMA quick_check`.

Дополнительно можно проверить данные вручную:

```bash
sqlite3 T:/AdminSTO/autoservice.db "SELECT id, name, maintenance_stars, tuning_total FROM clients ORDER BY id;"
```

## Ограничения

- Таблица `appointments` («Записи») не заполняется — сценарий покрывает
  клиентов, заказы и лояльность.
- Скрипт работает с базой схемы текущей версии приложения; если в будущем
  появятся обязательные колонки, `INSERT`-ы нужно будет дополнить.
- `--force` удаляет только строки тестового набора (клиенты 2–12, связанные
  заказы и справочники с `id` 1–9 / 1–7); данные, созданные в приложении,
  остаются на месте.
