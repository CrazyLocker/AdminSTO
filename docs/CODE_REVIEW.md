## Оставшиеся замечания

### 1. Дублирование и архитектура

1. **`service_parts` без защиты от дублей.** В основной структуре связей
   (`service_parts`) нет уникального индекса по `(service_id, spare_part_id)`,
   а `AddServicePartDialog` при добавлении делает `INSERT`. Повторное
   добавление пары создаёт вторую строку. Для legacy `service_spare_parts`
   обновление реализовано. *Рекомендация:* уникальный индекс + upsert либо
   проверка существующей пары в диалоге.
2. **Три API доступа к данным.** `Database`, `DatabaseFactory`,
   `DataStore` дублируют часть фасада. *Рекомендация:* оставить один слой.
3. **`ServicePartHelper` не используется** — фактическая логика в
   `AutoAddSparePartService`. *Рекомендация:* удалить или подключить.
4. **`ReportGenerator` вызывается только тестами.** `ReportView` уже берёт
   данные из `StatisticsService`, а PDF-экспорт отчёта в UI не подключён.
   *Рекомендация:* подключить рендер к `ReportData` или удалить класс.

### 2. Ресурсы и фоновые задачи

1. **`ScheduleService.cancelScheduledBackup()` не отменяет `ScheduledFuture`.**
   Метод обнуляет `Runnable`, но задача продолжает выполняться; выключение
   авто-бэкапа в настройках не останавливает её до перезапуска приложения.
   *Рекомендация:* хранить `ScheduledFuture<?>` и вызывать `cancel(false)`.
   Это единственное известное ограничение, влияющее на поведение настроек.

### 3. Потенциальные `NullPointerException`

1. **`WorkOrder.getClient()` / `Appointment.getClient()`.** Штатная загрузка
   через `LEFT JOIN` подставляет пустого клиента, поэтому на практике NPE не
   воспроизводится; но `new WorkOrder()` и внешние вызовы допускают `null`, а
   часть view-кода разыменовывает `getClient()` без проверки. *Рекомендация:*
   `Objects.requireNonNull` в модели либо отображение «Без клиента».
2. **`AbstractDatabase.getConnection()` при неинициализированном пуле.**
   `dataSource.getConnection()` без проверки; `DatabaseFactory` создаёт
   объект лениво. *Рекомендация:* явный `IllegalStateException` с понятным
   сообщением.
