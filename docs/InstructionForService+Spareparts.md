# Связи «услуга → запчасть»: как работает сейчас

> **Назначение:** описать текущую реализацию связей услуг и запчастей: схему,
> интерфейс, автодобавление в заказ и известные ограничения.
> **Актуализировано:** 18.11.2026
> **Версия ПО:** 1.2.0

## 1. Что изменилось

Раньше связь была жёстко зашита в услугу полями `oilVolume`, `usesOil`,
`sparePartName`, `sparePartQuantity`. Сейчас связи хранятся в БД и
настраиваются в интерфейсе; услуга может иметь несколько запчастей с разным
количеством и признаком обязательности. Задача из
`docs/archive/`-периода выполнена — этот документ описывает фактическое
поведение, а не план.

## 2. Схема данных

| Таблица | Роль |
|---|---|
| `service_parts` | Основная структура: `service_id`, `spare_part_id`, `quantity`, `is_required`, `created_date` |
| `service_spare_parts` | Legacy-структура: `service_id`, `spare_part_id`, `quantity`, `unit_type`, `active` |
| `service_spare_parts_lists` | Legacy-списки запчастей для услуги (`service_id`, `created_date`, `active`) |
| `service_spare_parts_list_items` | Элементы legacy-списков (`list_id`, `spare_part_id`, `quantity`, `unit_type`) |
| `to_parts` | Расходники ТО по модели автомобиля |
| `order_parts` | Снимок запчастей в конкретном заказе (имя, цена, количество, единица) |

Модели: `model/ServicePart` (основная связь), `model/ServiceSparePart`,
`model/ServiceSparePartsList`, `model/ServiceSparePartsListItem`.

## 3. Интерфейс

**Настройки → Связи** — дерево «услуга → запчасти» (`ServicePartsTreeTableView`):

- **Добавить связь** — диалог `AddServicePartDialog`: выбирается услуга и
  отмечаются запчасти; для каждой создаётся строка `service_parts` с
  количеством 1 и признаком «обязательная».
- **Изменить связь** — тот же диалог с предвыбранными запчастями: новые
  отмечаются и добавляются, снятые — удаляются.
- **Удалить связь** — с подтверждением; удаляется выбранная пара.
- **Обновить** — перечитывает связи из `DataStore`.

Кнопок «Очистить дубликаты» больше нет: они удалены вместе с методом
`deleteDuplicateServiceSpareParts()`. Для legacy-таблицы
`service_spare_parts` повторное добавление пары обновляет существующую запись
(`DataStore.addServiceSparePart()` ищет связь в кэше/БД и делает `UPDATE` по
`id`), поэтому дубликаты там не появляются.

## 4. Автодобавление запчастей в заказ

`AutoAddSparePartService.getSparePartsByService(serviceName)` собирает запчасти
из всех поддерживаемых структур: `service_parts`, активных
`service_spare_parts_lists` и активных `service_spare_parts`. При добавлении
услуги в диалоге создания/редактирования заказа (`CreateOrderDialog`,
`EditOrderDialog`) показывается список связанных запчастей с количеством;
пользователь может снять лишние, после чего строки добавляются в заказ.

В заказе хранится снимок (`order_parts`): имя, цена, количество и единица
измерения на момент оформления. Поэтому изменение справочника или связи не
переписывает уже созданные заказы. Остатки запчастей списываются при
сохранении заказа и возвращаются при отмене редактирования или удалении.

## 5. Проверка

- `DataStoreRelationsTest` — добавление/обновление/удаление связей, списки,
  автомобили клиентов, ТО и настройки.
- `AutoAddSparePartServiceTest` — сбор запчастей по услуге.
- `DataStorePersistenceTest` — сохранение `ServicePart` и повторная загрузка.
- Ручной сценарий: Настройки → Связи → добавить пару, создать заказ с этой
  услугой, убедиться, что запчасть предложена и списана со склада.

## 6. Известные ограничения

1. В основной структуре `service_parts` нет уникального индекса по паре
   `(service_id, spare_part_id)`: повторное нажатие «Добавить связь» с той же
   парой создаст вторую строку. Редактирование через «Изменить связь» работу
   с существующими парами выполняет корректно.
2. `AutoAddSparePartService` объединяет три структуры связей; при наличии
   одинаковой пары в нескольких структурах запчасть может быть предложена
   дважды — проверяйте список перед добавлением.
3. Класс `utils/ServicePartHelper` в прод-коде не используется; фактическая
   логика — в `AutoAddSparePartService`.
